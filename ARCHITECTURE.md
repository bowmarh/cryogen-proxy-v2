# Architecture

```
Browser (public/index.html)
 ├─ fetch /api/roster, POST /api/members/{zwiftId}       → api/server.js → WordPress plugin on Hostinger
 │     /members                     member records (tier, status, offboarding), read + PATCH
 │     /zwift/public/clubs/2740/0   live roster from ZwiftRacing.app
 ├─ fetch /api/proxy?endpoint=rides|ttt-sheet           → api/server.js → Google Sheets (gviz JSON)
 ├─ fetch /api/state, POST /api/signups|rsvps|rides|…   → api/server.js → Upstash Redis (shared)
 ├─ profile calendar settings /api/me/calendar         → api/server.js → private /api/cal/{secret}.ics feed
 └─ localStorage                                         affiliation history (per browser)
```

## Frontend (`public/index.html`)

The dashboard keeps its no-build setup. `public/index.html` contains the shell and most UI logic; small, self-contained features are being extracted into `public/js/` over time (the personal calendar settings UI is the first module). Tabs: Team Overview, Racing Dashboard, Events & Sign-Up, Social Rides, Members, plus a profile page.

- **Roles:** admin, moderator and member. Admin and moderator passwords are checked by `POST /api/login` against the `ADMIN_PASSWORD` / `MOD_PASSWORD` environment variables. Members either sign in with their cryogen.team account (verified) or pick themselves from the live roster by name or Zwift ID (guest). The role is kept in `sessionStorage`.
- **Data loading:** `loadLive()` reads `/api/roster`, which merges the club roster with the WordPress member records by Zwift ID. The response includes the roster's last successful update time and whether it is stale; the UI labels stale data and never substitutes sample riders.
- **Member edits:** tier, status and off-boarding checkboxes call `POST /api/members/{zwiftId}` (staff only). The server PATCHes the WordPress record, reads it back, and reports an error if a field didn't save. The browser never holds WordPress credentials.
- **Shared state:** sign-ups, series locks, club-created rides and RSVPs come from `/api/state`. Every write returns the full new state, which the page re-renders from.
- **Escaping:** everything people type is shown to other people, so it's rendered through `esc()`. Values passed to click handlers go through `data-*` attributes, never inline into the JS.
- **Local state:** affiliation history is still saved to `localStorage`.

## Proxy (`api/server.js`)

A plain Node.js request handler:

- `POST /api/login` with `{role, password}` checks the role's password environment variable. It returns `{role, token}` on success (an HMAC-signed token, valid 12 hours), 401 on a wrong password, and 503 if the variable isn't set.
- `GET /api/proxy?endpoint=rides|ttt-sheet` reads that tab of the Google Sheet and returns `{rides, headers, updated}` or `{headers, rows, updated}`. Dates become `YYYY-MM-DD`. Only the named tabs are allowed.
- Shared data, stored in Upstash Redis hashes `cg:signups`, `cg:locks`, `cg:rides` and `cg:rsvps`:

  | Route | Who |
  |---|---|
  | `GET /api/state` | anyone |
  | `POST /api/signups`, `/api/rsvps`, `/api/rsvps/cancel` | anyone |
  | `POST /api/signups/remove`, `/api/rides`, `/api/rides/remove` | admin or mod (Bearer token) |
  | `POST /api/signups/clear`, `/api/locks` | admin |

- TTT week (Redis `cg:ttt:week`, `cg:ttt:signups`, `cg:ttt:assign`, `cg:ttt:archive`). Responses depend on the caller: comments are staff-only, and line-ups are hidden from members until published.

  | Route | Who |
  |---|---|
  | `GET /api/ttt`, `GET /api/ttt/archive?id=<date>` | anyone |
  | `POST /api/ttt/signup` (sign up or update), `/api/ttt/withdraw` | anyone, while sign-ups are open |
  | `POST /api/ttt/assign`, `/api/ttt/auto-assign`, `/api/ttt/status` (open/publish), `/api/ttt/teams`, `/api/ttt/new-week` | admin or mod |

  Starting a new week archives the current one with its line-ups and carries the teams over. Auto-assign places available, unplaced riders into their preferred teams (two for double-up), earliest sign-ups first, up to each team's max.

- When run locally, all other paths serve files from `public/`.

The file exports its handler for Vercel. `vercel.json` rewrites `/api/*` to it, and `npm start` runs it as a local server. Mutating requests with an `Origin` header must come from the configured `SITE_URL` origin; CORS preflights advertise only that origin.

## Social rides extras (taken from the ZRL)

*Reminder.* `runRidesSchedule` (run by the cron tick, which reports it as `ride-reminder`) announces each club-created ride that is today or tomorrow (UTC date) once in the club channel: when, route, distance and pace, how many are riding, how many places are left, the Zwift link and where to RSVP. The mark is `<ride id>:reminder` in `cg:rides:sent`. Rides copied in from the club sheet have no RSVPs in the dashboard and are not announced. *Export:* `GET /api/rides/export[?id=<ride id>]` (staff) returns `{filename, csv}` with the RSVPs of every ride from today on, or of one ride (ride, date, time, rider, when they RSVP'd), formula-looking names neutralised. *In the page:* past rides move into a collapsed **Past rides** list with how many RSVP'd; staff get an **⬇ RSVPs (CSV)** button; the profile page has **My rides** (the rides the signed-in rider has RSVP'd to, from today on, plus how many earlier ones). RSVPs are stored under the name in the member's sign-in (the WordPress name), which can differ from their roster name, so My rides matches either (`memberName` is kept in the session when they sign in).

## Club roster cache

The roster comes from ZwiftRacing.app through the WordPress plugin, which answers 429 when asked too often. Each server instance used to ask on its own. The slimmed rider list is now kept in Redis (`cg:roster:riders`): reused for 10 minutes by every instance, and the last good copy is served if the source fails. Member records are not cached there; they are read each time the 5-minute in-memory cache expires.

**One rider, one sign-up.** TTT sign-ups are keyed by the lower-cased name, so the same rider could end up twice (a guest and a signed-in sign-up, or two spellings). Guest names have their spacing collapsed; a sign-up whose Zwift ID is already on the week updates that sign-up (keeping its name, queue place and team places); withdrawing removes every sign-up carrying the rider's Zwift ID; My TTT finds the sign-up by Zwift ID; and `mergeDuplicateSignups` merges any existing duplicates whenever the TTT page loads (earliest name and place kept, latest answers win, team places combined up to 2, a captaincy follows).

**TTT extras (taken from the ZRL).** *Race-day summary:* in `runTttSchedule`, on the week's date (UTC, 24 hours, and only until the next-week rollover) one `digest` event (claimed once per week in `cg:ttt:sent`) posts to the admin channel how many teams are racing, whether the line-ups are published, teams under four riders, teams with no captain and available riders in no team. *Ask for riders:* `POST /api/ttt/recruit` (staff) posts to the club channel how many have signed up and how many teams are short, with the link; sign-ups must be open (409 otherwise) and it is limited to once a day (`<week id>:recruit:<UTC date>`, 429 after). *Exports:* `GET /api/ttt/export?kind=lineups|results[&season=<id>]` (staff) returns `{filename, csv}`: this week's line-ups (team, level, zone, rider, captain, double-up) or the season's results (date, week, team, level, zone, position, time, did not finish, captain, riders), with formula-looking cells neutralised. The TTT Week staff panel has the buttons, and the Season tab has the results export. My TTT already carries a rider's history, so there is no separate season view for riders.

## TTT Season page

`GET /api/ttt/season` (public) feeds the **TTT Season** tab. `seasonSummary()` reads up to the latest 60 archived weeks, plus the current week once it has results, and returns totals, per-team stats (weeks, best and average place, podiums, DNFs), a rider leaderboard (weeks ridden, times captain, podiums; top 25) and a week-by-week list. A team counts for a week only if it had riders or a result. It uses only names, line-ups, captains and results, never comments or Zwift IDs. 

**Seasons.** A season is a name and a start date (Redis `cg:ttt:seasons`, JSON `[{id: <start date>, name, start}]`); it runs until the next season starts. `GET /api/ttt/season?season=<id>` returns that season's summary plus the list of seasons to choose from; the default is the latest. Until the first season is defined there is a single "All weeks" entry (the old behaviour), and once one exists, weeks before it appear as "Earlier weeks". Staff (admin or moderator) add a season with `POST /api/ttt/seasons {name, start}` (must start after the latest) and remove one with `POST /api/ttt/seasons/remove {id}`, whose weeks then fall back into the season before it. Nothing is ever deleted: seasons only decide which archived weeks the page shows.

## ZRL round sign-up

Logic lives in `lib/zrl.js` (a factory that `api/server.js` wires up; not in `api/`, since every file there becomes a public function). Redis keys: `cg:zrl:round` (name, start, closes, weeks, open, published, teams), `cg:zrl:signups` (one field per rider), `cg:zrl:assign`, `cg:zrl:archive`, `cg:zrl:sent`. Regions are `eu`, `am`, `ap` (Asia-Pacific).

- `GET /api/zrl` is public: the round, the demand per region (riders, teams, places still to fill) and the sign-up pool. Comments, Zwift IDs and preferred team are staff-only.
- `POST /api/zrl/signup` and `/withdraw` use `identify`, so a signed-in member can only sign themselves up. At least one time zone is required when racing; category defaults to the rider's profile category.
- Staff only: `POST /api/zrl/round` (starts a round, archives the previous one, keeps the teams, posts "sign-ups open" to Discord), `/status` (open or closed, published) and `/teams` (replace the team list).
- `POST /api/zrl/import {tab, apply, regions}` (staff) reads the team board tab of the club Google Sheet: one block of columns per team (zone or colour label, name, "Division n", grade, a Rider header row, one rider per row; blocks differ in width). Without `apply` it returns a preview; with it, teams and rosters (`cg:zrl:assign`) are replaced and riders without a sign-up get one. Missing Zwift IDs are filled from the club roster by exact name. The board's EMEA/AMERICAS labels give a time zone; colours do not, so staff pick those. Teams may carry `division` and `grade`.
- `POST /api/zrl/import-signups {tab, sheet, apply}` (staff) reads the form responses tab (one row per submission): Zwift ID from the ZwiftPower link, else a bare number, else the club roster by name; the latest row per rider wins. Time zones come from the primary and backup league labels (words like EMEA/Americas, else the UTC race time read as a local evening, else the colour). A rider's own sign-up on the page is never overwritten; sheet-made entries (`source: 'sheet'`) are refreshed. Staff also see the league, commitment (`commit`), previous team (`prevTeam`) and `source`. Sheet tabs are read with `fetchGrid`, which cannot tell an unknown tab name from the first tab (Google answers both the same), so each importer checks the layout it expects.
- `POST /api/zrl/auto-assign {apply}` (staff) suggests, or with `apply` makes, a team for every rider racing who has none (`planAssignments`, a pure function). Rules: a rider may ride their own category or a weaker one (team category = the last letter of its grade); the team must be in one of the rider's time zones and have a free place (10); full-season riders before reserves, those who named a team first, then first come; each goes to the eligible team nearest to full so teams complete, a close category match breaking ties; a captain-minded rider becomes the captain of a team that has none. Riders who cannot be placed are listed with the reason. `POST /api/zrl/assign {key, team}` (staff) moves one rider, or takes them off with an empty team.\n- `GET /api/zrl/export` (staff) builds the registration list for WTRL (which has no public sign-up, so captains register by hand): per team a readable block (name, division, grade, time zone, captain, numbered riders with Zwift ID and category), a plain list of Zwift IDs, the problems (no captain, not 10 riders, missing IDs or categories), riders with no team, and one CSV. CSV cells that start with `=`, `+`, `-` or `@` are prefixed with an apostrophe so a name can never run as a spreadsheet formula.\n- `GET /api/zrl/mine` (signed-in member) is the rider's own view: their sign-up, their team once `published` (names and categories only), and, if they are a team's captain, that team straight away with Zwift IDs, the registration text and the problems to sort out (`myZrl`). Comments, other teams and other riders' IDs never appear. The ZRL page shows it above the sign-up card.\n- Publishing (`POST /api/zrl/status {published: true}`, with a 📣 Publish rosters button in the staff panel) lets riders see their team and, the first time per round (claimed in `cg:zrl:sent` as `<round id>:published`), posts "the rosters are out" to the club channel (counts per time zone, where to look; no rider names) and a to-do list to the admin channel (teams without a captain or short of riders, riders without an ID or team). `announce: false` publishes silently and does not use up the announcement.\n- WTRL fixes each league's race time by its colour (not by division or men/women). `LEAGUE_ANCHORS` in `lib/zrl.js` holds, per colour, the city and local time it is anchored to (the violet cell of the 2026/27 league table); `leagueSlot(label, start)` turns that into `Tue HH:MM UTC` for the round's first race day, so daylight saving is followed. Every team in `GET /api/zrl` carries it as `wtrlSlot`, the Setup tab shows it beside each league with a ✓ or amber, and `POST /api/zrl/league-times` (staff) applies it to every team whose league names a colour, leaving other teams alone.
- Weekly management, per race week (`round.weeks`, a week every 7 days from the first race; `weekDate`). Stored in the hash `cg:zrl:weekly`: `a:<week>:<zwid>` is a rider's answer (`yes`, `maybe`, `no`) and `l:<week>:<team id>` is the JSON list of Zwift IDs the captain picked. It is cleared when the next round starts (the old answers go into the archive snapshot). `POST /api/zrl/availability {week, status, zwid?}` (a rider for themselves, a captain for their own team's riders, or staff; the rider must be on a team; an empty status clears it). `POST /api/zrl/lineup {week, team, zwids}` (the team's captain or staff; only riders on that team with a Zwift ID, at most `round.racing` of them, nobody who said no; an empty list clears it). `GET /api/zrl/mine` carries each rider's `weeks` (own answer, whether picked, the line-up names) and, for a captain, per team per week the line-up and every rider's answer. `GET /api/zrl` carries the raw `weekly` answers and line-ups for staff only, which the staff team panel uses to edit a team's line-ups and each rider's answer (same routes as the captain, no captain login needed). `GET /api/zrl/weekly` (staff) is the overview behind the 📅 Weeks tab (line-up size and yes/maybe/no counts per team and race). The ZRL health row warns when the next race is within three days and teams have not picked a full line-up (`healthRow` takes the weekly data as `data.weekly`).
- Race-week reminders run in `zrl.runSchedule` (the same tick as the sign-up reminder and close), once the rosters are published, per race week and only until the race day starts (00:00 UTC on that date): five days before, the club channel asks riders whether they can race (`<round id>:w<i>:avail` in `cg:zrl:sent`); two days before, the ZRL admin channel lists the teams that have riders but no full line-up (`:w<i>:lineup`; nothing is posted, and the claim is kept, when every team is sorted). A scheduler that was down catches up: a reminder whose time has passed fires once if the race has not started.
- WTRL registration tracker. WTRL has no API, so captains register by hand and say so: `POST /api/zrl/wtrl-registered {team, registered}` (the team's captain or staff; `registered: false` takes it off) stores `r:<team id>` in `cg:zrl:weekly` (so it clears with the round). Staff set the deadline with `POST /api/zrl/wtrl-deadline {date}` (stored as `round.wtrlDeadline`, 23:00 UK on that day; empty removes it). Teams in `GET /api/zrl` carry `wtrlRegistered`; the captain view carries `registered` and the round's deadline. The health row counts teams with riders that are not registered once a deadline is set, and `runSchedule` posts the list to the ZRL admin channel once, three days before the deadline (`<round id>:wtrl3`; nothing if all are registered). `load()` now returns `weekly` as well.
- Rollover: `POST /api/zrl/round {name, start, closes, weeks, carryRiders}` archives the current round (teams, sign-ups, placements and the weekly answers) and starts the next. Teams always carry over, with race times recalculated from the league colour for the new dates (`leagueSlot`, empty when the league names no colour) and `captainLocked` reset. Without `carryRiders` captains are cleared and the round starts with no riders. With `carryRiders: true` every rider who is in and on a team is copied (marked `carried`, original sign-up time kept) onto the same team, and a captain who is among them stays captain. The option is ignored when there is no earlier round. The Setup tab's "Start a new round" card has the tick-box (on by default) and a confirm that says how many riders stay.
- Standings post and export. `POST /api/zrl/post-standings` (staff) posts the standings to the ZRL club channel, one block per division ("1. Team · 120 pts (best 1st)"), split into several messages so none passes Discord's 2000-character limit, with a link to the dashboard; it needs at least one result (409) and is limited to one post every five minutes (`<round id>:standings:<5-minute bucket>` in `cg:zrl:sent`, 429 after). `GET /api/zrl/results-export?kind=standings|results` (staff) returns `{filename, csv}` for the browser to save: the standings (division, rank, team, points, races, best finish and each race's position and points) or the results race by race (race, date, team, division, league, position, points, note). Cells that start with `=`, `+`, `-` or `@` are neutralised with an apostrophe (`csvCell`). The Results tab shows the three buttons under the standings.
- Change log. Every successful `POST` to a ZRL route is recorded by `logChange` (called from `handleZrl`) as a short entry, newest first, in the capped list `cg:zrl:log` (500 kept): time, role (`admin`, `mod`, `member` or `guest`), the member's name when there is one, the route, and a description built only from a whitelist of fields (team, week, status, name, key, zwid and the like; lists are counted, never copied; anything named like a password, token or secret is skipped). Requests that are refused are not logged. `GET /api/zrl/log` (staff) returns the latest 100, shown in the Setup tab under Recent changes.
- Category check. `GET /api/zrl/category-check[?fresh=1]` (staff) compares each racing rider's declared category with their ZwiftPower category (`zpCategory`, with the vELO category name for context) from the ZwiftRacing.app club list (`https://api.zwiftracing.app/api/public/clubs/<ZWIFT_CLUB_ID, default 2740>`, the key in `ZWIFTRACING_API_KEY`). That API allows one club request every ten minutes, so the reduced list (`{<zwift id>: {z, v}}`) is kept in `cg:zrl:zrclub`, refreshed after an hour, or on request (`fresh=1`) but at most every ten minutes; if they answer 429 or cannot be reached the kept copy is used and the answer says `stale`. It returns `understated` (declared weaker than ZwiftPower, or no category declared), `misplaced` (placed on a team whose category, the last letter of its grade, is weaker than the rider's ZwiftPower category, using the same `catGap` rule as auto-assign), `overstated` (declared stronger: harmless) and `notFound` (no Zwift ID, not asked about yet, or ZwiftRacing.app has no profile for the ID: `noProfile`). Racing riders with a Zwift ID who are not in the club list are asked about in one batch request (`POST /api/public/riders` with their IDs as numbers, which a standard key may make once every ten minutes; opted-out and unknown riders are omitted from the answer, which is how `noProfile` is known). Those answers are kept in `cg:zrl:zrextra` for a day (`{<zwift id>: {z, v}}` or `{none: true}`), are marked `outsideClub` in the rows, and a refusal or failure only adds a `lookupNote`. Riders are matched by Zwift ID. The Riders tab shows it as Category check, with a Set to <ZwiftPower category> button that uses `signup-edit`.
- Race check. `GET /api/zrl/event-check?id=<Zwift event id>` (staff) reads one race's finishers from the ZwiftRacing.app organizer API (`https://api.zwiftracing.app/api/public/results/:id`, the key in `ZWIFTRACING_API_KEY`; this address works, the plain `zwiftracing.app` one serves the website). The response has `eventId`, `title` (e.g. "... Open Shamrock League Division 4 - Race 3"), `type`, `subType`, `time`, `distance` and `results[]` (`riderId`, `name` with HTML entities and the rider's team tag, `category`, `time`, `gap`, `position`, `positionInCategory`, ratings). The race week comes from the race's own `time`: a race belongs to week `i` when it starts between 12 hours before and 36 hours after that week's first-race date (UTC), so a Wednesday-morning UTC start still counts for the week before; a race outside every week of the round returns `outsideRound: true` and `week: null` (the title's race number repeats every round, so it is only the fallback when there is no `time`). The title is also parsed into league colour, division and race number, used to mark which of our teams the title names (`named`). Our riders are matched by Zwift ID, never by name, and a rider's team is their team in the *current* round, so a past round's race lists the teams its riders are on now. Per team it returns who raced (position, category) with whether the captain had picked them, and who was picked but is not in the results. A team appears if a rider of ours finished, or if the title names its league and division and it had a line-up. 429 (one results request a minute), 401 and unknown events become plain messages. It does not give team positions or points: those come from WTRL and are entered in the Results tab. The Results tab shows it as "Check a race".
- ZwiftRacing.app lookup. `GET /api/zrl/zr-event?kind=<results|zp|rider|club|categories>&id=<n>&host=<site|api>` (admin only) calls one documented endpoint of the ZwiftRacing.app organizer API (`/api/public/results/:id`, `/api/public/zp/:id/results`, `/api/public/riders/:id`, `/api/public/clubs/:id`, `/api/v2/public/categories`) on `zwiftracing.app` or `api.zwiftracing.app` with `ZWIFTRACING_API_KEY` sent raw in `Authorization`. It returns the status, the time taken, the address asked (never the key), `isPage` (true when the answer was the site's web page rather than data, in which case only the first 600 characters are returned), the *shape* of the answer (field names and types) and the answer cut at 150 KB. Their errors (401, 429 with `retryAfter`) come back as they are. It exists to see what the API returns before anything is built on it. The first real run of `/api/public/results/:id` on `zwiftracing.app` returned the site's "Page not found" page with status 200, so the working address is still to be found. The API gives individual finishers for one event and nothing for ZRL teams, divisions or points, and allows one results request a minute. `GET /api/zrl/zr-probe?rider=<id>&event=<id>` (admin only) tries all of them at once (categories, the rider and the event results, each on both addresses, in parallel so it fits the function's 10 s limit) and returns a short summary per attempt: status, whether it was JSON, the website or an error, and the first keys or words. The Results tab's "Run all checks" button uses it.
- Results and standings. Staff record, per race week and team, the finishing position and the points scored: `POST /api/zrl/results {week, rows:[{team, pos, pts, note}]}` (staff; positions are whole numbers from 1, points numbers from 0, blank clears a row; the note is staff-only) stored in `cg:zrl:results` (`<week>:<team id>` -> `{pos, pts, note}`). `GET /api/zrl/standings` (open to everyone) groups the teams that have a result by their division (or league, or "All teams") and ranks them by total points, then best finish, with ties sharing a rank (`standingsOf`); staff also get the raw `entries` for the entry form. The ZRL page shows the standings card to riders and the staff 🏆 Results tab has the entry grid per race. Starting the next round archives the results with the round (`snapshot.results`) and clears them.
- Rider's season. `GET /api/zrl/mine` carries, for a rider on a published team, one entry per race week with their own answer (`mine`), whether the captain picked them (`picked`), the line-up names and `result` (the team's `{pos, pts}` for that race from the results, or null). The ZRL page's "Your season" block (the same card as the Yes / Maybe / No buttons) adds a summary: races picked for out of the races so far, times the rider said yes, and the team's points so far. Team results are the same ones the open standings show; nothing personal about other riders is added.
- The change log and help cards also cover the **TTT Week** and **Social Rides** tabs. `handleTtt` and `handleData` call `logChange(req, path, body, {staffOnly: true})` after every successful `POST`, so what staff change there (assigning, publishing, creating or removing a ride) joins the same list as the ZRL's, while riders' own sign-ups, withdrawals and RSVPs are left out so they cannot bury it. Each tab shows its own entries (`ttt/…`; `rides`, `rsvps`, `signups`) in a lazily loaded **Recent changes** panel for staff, read from `GET /api/zrl/log`, and a collapsed ❓ card (`plainHelp`) with the steps for riders or for staff.
- Round readiness. `GET /api/zrl/readiness` (staff) runs `readiness()`: an ok/todo checklist (riders placed, Zwift IDs, captains, race times, roster size, nobody below class, rosters published, WTRL deadline set and teams registered, race 1 line-ups) with a count, a sentence and the tab to fix each in. The ZRL staff view shows it as a card (`zrlReadyCard`) above the tabs, open until everything is green; it reloads after any change.
- Points calculator. `POST /api/zrl/score` (staff, saves nothing, not logged) runs `scoreRace()` for the 2026/27 rules: per rider FIN = starters − position + 1, podium bonus 10/8/6/4/2 for the top five, plus FAL and FTS points entered by hand; no heart rate gives zero for an A rider and half for B to D, ZPower halves, and the two multiply. The team total is the sum of the riders given. The Results tab has a 🧮 button per team that opens a calculator pre-filled with that week's line-up and fills the team's points box; the position and the league points stay typed by hand.
- Results import. In the Results tab's **Check a race** card (`GET /api/zrl/event-check`), every team of ours that raced in a race inside the round has a **🧮 Work out points** button (`zrlCalcFromEvent`). It opens the points calculator with the starters set to the riders in the results, the captain's line-up as the rows, and each rider's finishing position and ZwiftRacing category filled in; only FAL and FTS points are typed. Nothing new on the server.
- TTT calculator. The same `POST /api/zrl/score` with `mode: "ttt"` runs `scoreTtt()`: no individual points; the team time is the fourth finisher's time (seconds or m:ss.s), fewer than four finishers is a DNQ, and ZPower riders over 40% of the squad raise a warning. The calculator card has a Points race / Team time trial switch, and opens in TTT mode when the race check reports a time trial. "Put in the note" writes the team time (or DNQ, with 0 points) into the team's note box; the position still comes from WTRL.
- Race results post. `POST /api/zrl/post-race` (staff, body `{week}`) posts one race's saved results to the ZRL club channel, by division, each team's position and points (staff notes are left out), split below the Discord limit, once per five minutes per race (`cg:zrl:sent`). The Results tab has a **📣 Post race N to Discord** button next to Save race.
- League points. A result now carries the position, `field` (teams that started in the division), `flag` (`ineligible` or `dnq`) and the calculator's rider points (`score`, `fin`, `fal`, `fts`, `best`). `resultEdits` works the league points out as WTRL does: first of N teams gets N, one less each place, halved for an ineligible rider, zero for a DNQ; without a position and field the typed points stand. Standings break ties by league points, then total FIN, FAL, FTS, then the best single rider finish (our best team finish last); equal on all of them share a rank. The calculator's **Keep these rider points** stores the rider totals on the row; it no longer writes the team's league points.
- Score all teams. `POST /api/zrl/score-all` (staff, saves nothing, not logged) runs `scoreRace`/`scoreTtt` for every team in one call from a race check and lists the riders whose category is stronger than the team's class (`belowClass`); a bad team is reported on its own. The race check card's **Score all teams from this race** fills every row (rider points, or team time / DNQ) and marks such teams Ineligible; nothing is saved until Save race. FAL and FTS points are not in the results and are added per team with 🧮. The Results tab also has a collapsed **Race-day runbook** card.
- Failed jobs. `handleCron` runs the TTT, ZRL, Rides and Backup jobs separately so one failure cannot stop the others; a failure is posted to the ZRL admin channel (once per job every six hours, `cg:cron:alerts`) and kept in `cg:cron:failed` until the next clean run, which turns the health panel's scheduled-runs row red with the job and error.
- My next race and installing. A placed rider's ZRL page opens with **Your next race** (`zrlNextRaceCard`): the next race date plus the league's fixed UTC start (`zrlRaceMoment`, from the team's `slot`) shown in the rider's own time zone, a countdown, whether they are in the line-up, and big Yes / Maybe / No buttons that use the same availability route. The dashboard is installable: `public/manifest.json`, icons, and `public/sw.js`, which only keeps the page for offline starts (page loads are fetched fresh first; `/api/` is never touched). After sign-in on a phone, a one-time bar offers Install (Android/Chrome) or the Share > Add to Home Screen steps (iPhone).
- Help cards. The ZRL page opens with a collapsed ❓ card: the steps for riders, for a captain (shown instead when the signed-in member captains a team), or the staff checklist for a round (`zrlHelpCard`). It is page text only; update it when a step changes.
- Subs finder: `GET /api/zrl/subs?team=<id>&week=<n>` (the team's captain or staff) returns how many are picked for that race and how many more are needed, the bench (the team's own riders with a Zwift ID who are not in the line-up and did not say no, yes before maybe before no answer) and a pool of racing riders with no team who are in the team's time zone and whose category may ride it (same `catGap` rule as auto-assign; staff also get each rider's `key`). `rosterFull` is true when the team already has the full roster. In the page it is the 🔎 Find subs button under each race of the line-up editor; staff get an Add to team button (the existing assign route), captains are told to ask the staff. Zrl routes now receive the query string as a third argument.
- Past rounds (staff, Setup tab → Past rounds). `GET /api/zrl/archive` lists the archived rounds (name, first race, teams, riders) and `?id=<round id>` returns one: teams with captain and riders, and its standings with the raw result entries. `POST /api/zrl/archive-edit {id, name?, week?, rows?}` renames it and/or corrects its results (the same validation as live results, `resultEdits`). `POST /api/zrl/archive-delete {id}` (admin only) removes it. `POST /api/zrl/round-delete {confirm}` (admin only; `confirm` must be the current round's first-race date) deletes the current round and everything stored for it (sign-ups, placements, weekly answers, results and its scheduled-post marks), for a test round started by mistake. Past rounds' sign-ups and placements are not editable, only the name and the results.
- Race-day digest. In `runSchedule`, once the rosters are published, on each race day (the UTC date of the week's first-race date, from 00:00 UTC for 24 hours) one summary goes to the ZRL admin channel (`<round id>:w<i>:digest` in `cg:zrl:sent`, so once per race, whatever state the week is in): how many teams are racing, whether every team has a full line-up (or which do not), teams with no race time, teams not marked registered on WTRL (only when a deadline is set) and how many riders have not said whether they can race. It complements the five-day rider ask and the two-day line-up chase and is the staff's last look before racing. A scheduler that was down still posts it if it runs during the race day.
- Growth card and recruit post. The Teams tab (staff) opens with a card per time zone: places open on its teams, riders interested with no team, or "no team yet", each with a 📣 Ask for riders button (Asia-Pacific highlighted). `POST /api/zrl/recruit {region}` (staff, default `ap`) posts to the ZRL club channel how many places are open and the teams' distinct race times (up to three), or, for a zone with no team, that a team is wanted and how many are interested. It needs sign-ups open (409 otherwise) and is limited to one post per zone per day (`<round id>:recruit:<zone>:<UTC date>` in `cg:zrl:sent`, 429 after).
- `POST /api/zrl/round-edit {name, start, closes, weeks}` (staff) corrects a round's name and dates in place (the id follows the first-race date): sign-ups, teams and placements stay, nothing is announced, and the reminder and close events for the old and new date are cleared so they fire on the new dates. Refused if an archived round already started that day.\n- `POST /api/zrl/signup-edit` and `/signup-remove` (staff) are the override: add a rider (with or without a Zwift ID), change any detail of any sign-up (racing or not, time zones, category, commitment, captain, preferred team, comments, team), or correct a name or Zwift ID, which moves the sign-up and its team place. Edits are marked `source: 'staff'` and `edited`, and the sheet import never overwrites a sign-up that has any source other than `sheet` (riders' own sign-ups carry none and are protected too). The ZRL page shows a ✏️ button on every row (including riders who are not racing) and a + Add a rider button.\n- Captains are automatic: after every `POST` to a ZRL route (an import, a move, a rider ticking the star) `afterChange` gives each team that has riders and no captain its first volunteer (the earliest sign-up with the star and a Zwift ID; the auto-assign preview uses the same rule). A captain is never replaced, and one that staff cleared by hand (`captainLocked`, set when the choice is emptied here or the ID is cleared in the team editor, unset when a captain is chosen) is not put back. `POST /api/zrl/captain {team, key}` (staff) chooses a team's captain from its own riders (must be on that team and have a Zwift ID; an empty key clears it). `POST /api/zrl/captains {picks:[{team,key}]}` (staff) does the same for several teams at once, all or nothing; the Teams tab shows a "Teams without a captain" card with a drop-down per team, a Suggest button (volunteers first, then earliest sign-up) and Save captains. Other volunteers in a team that already has a captain are listed as spare on the Rosters and captains card, with a drop-down to move them to a team that has none, where they become its captain.

## Backups

`lib/backup.js` (not in `api/`). It copies everything the ZRL and the TTT keep in Redis: the current ZRL round, the sign-ups, placements, weekly answers, results, archive and scheduled-post marks, and the TTT week, sign-ups, placements, archive and marks. Each copy is gzipped, base64-encoded and stored in the hash `cg:backup` as `<kind>:<ISO time>`. The scheduled tick takes one `auto` copy a day (quietly: it is not reported in `ran`, and nothing is posted) and keeps the last 14; `manual` copies (kept: 10) and `pre-restore` copies (kept: 5) are taken on request. Admin only (a moderator gets 403): `GET /api/admin/backups` lists them, `POST /api/admin/backup-now`, `GET /api/admin/backup-download[?id=]` returns the data as JSON for the browser to save (the current data when there is no id), and `POST /api/admin/restore {id, confirm: "RESTORE"}` replaces those keys with the copy after taking a `pre-restore` copy, so a restore can itself be undone. The Admin dialog has a Backups block, and the health panel's Backups row warns when the last automatic copy is over 36 hours old. These copies live in the same Redis as the data, so they protect against mistakes, not against losing the database: keep an occasional downloaded file as well.

## Member sign-in

Riders can sign in with their cryogen.team account instead of picking a name.

1. The "Sign in" button goes to `WP_SSO_LOGIN_URL` on WordPress. A snippet there logs the member in if needed, then redirects to `/api/auth/wp?t=<token>`.
2. The token is `base64url(JSON {zwid, name, exp, n}) + "." + base64url(HMAC-SHA256(WP_SSO_SECRET, first part))`. It must expire within 10 minutes and can be used once (nonce stored in Redis as `cg:sso:<n>`).
3. The server issues a 12-hour member session (same signing as staff sessions, `role: "member"`, with `zwid` and the roster name) and redirects to `/#sso=<session>`. The page reads the fragment, stores the token and removes it from the URL. Members whose WordPress record is `left` are refused.
4. With a member session, `identify()` forces the sign-up, withdrawal and RSVP routes to act as that rider whatever the request body says. A member session is never a staff role.
5. Guests (name-picker) can still write until `REQUIRE_MEMBER_LOGIN=1`; then they get a 401 asking them to sign in. Staff can still act for others.

`GET /api/auth/status` tells the page whether to show the button; `GET /api/me` returns the signed-in member's tier and status.

`GET /api/ttt/mine` (member session only) powers the **My TTT** card on the profile page: the rider's own sign-up for the current week, and once line-ups are published their team(s), zone, captain, teammates, waitlist place and result, plus up to 10 earlier weeks they rode (from the archive). Line-ups stay hidden until published, exactly as on the TTT page.

## Ride cover (leaders and sweepers for the weekly social rides)
`lib/cover.js` (factory `createCover`, routes under `/api/cover/*`, wired in `api/server.js` as `handleCover`). Replaces the old Google-Sheet ride sync on the Social Rides tab; the ZwiftHacks calendar iframe stays as the public view.
- Data (Redis, all hashes): `cg:cover:series` (a regular ride: weekday, local time and IANA zone, so it follows daylight saving; owner name and Zwift ID), `cg:cover:slots` (`<series>|<date>|<role>` → who; roles `leader`, `leader2` (back-up), `sweeper`, `sweeper2`), `cg:cover:approved` (zwid → may lead / sweep; staff manage it), `cg:cover:standing` ("most weeks" offers), `cg:cover:cancelled`, `cg:cover:optout` (withdrew from a date, so a standing offer is not put back), `cg:cover:sent` (each notice once). The coming four weeks of dates are derived from the series, not stored.

Every notice is claimed in `cg:cover:sent` so it goes once.
- Delivery (`notify`): a JSON POST to `RIDE_COVER_WEBHOOK_URL` first (Zapier/Make/Twilio turn it into WhatsApp; WhatsApp has no way to post into a group directly), Discord (`public`/`admin`) when it is unset or fails. Staff also get **Copy for WhatsApp** and **Open WhatsApp** buttons that carry the same call-out text (`GET /api/cover/callout`, WhatsApp bold) for hand-posting.

- Health: a "Ride cover" row warns about any ride in the next 7 days with no leader or sweeper and says whether the webhook is set.
- Page layout. The Social Rides page has three tabs (`ridesTabGo`, remembered in sessionStorage): **Ride cover** (default, with a badge counting rides in the next 7 days that lack a leader or sweeper), **Calendar** (the ZwiftHacks iframe, loaded only when opened) and **RSVP rides** (the one-off rides, help card and change log, plus the + New Ride button). Each series is one collapsed row showing its next date and status (covered / needs back-up / needs leader + sweeper), soonest first, with an "Only rides that need cover" filter; opening a row shows the next four dates and their four slots.
- Your season. `GET /api/me/season` (signed-in members only; `handleMeSeason`) answers one rider's record in one call: ZRL (`zrl.myZrl` over the races already run: picked for, availability answers, team points, podiums), TTT (the rider's line in the latest season's `seasonSummary(…, true).everyRider`), social rides (RSVPs, and how many were for rides already past) and ride cover (`cover.statsFor`: dates led or swept, cancelled ones left out, and the next three duties), plus a few earned highlights. The Results tab has a **🏅 Round recognition** button that previews the exact text before posting. ## Zwift Club Ladder
`lib/ladder.js` (factory `createLadder`, routes under `/api/ladder/*`, `handleLadder` in `api/server.js`, a **🪜 Ladder** tab). The ZwiftRacing.app Club Ladder is a 5v5 head-to-head format apart from the WTRL league.
- **Roster and categories.** Up to 15 riders (`cg:ladder:roster`, staff-managed). A rider's vELO category (Diamond, Ruby, Emerald, Sapphire, Amethyst, Platinum, Gold, Silver, Bronze, Copper) and rating come from the club roster the dashboard already caches (`fetchRoster().riders[].race.current`), so the module makes **no ZwiftRacing.app requests of its own** and cannot hit its rate limits.
- **The three-rank rule.** `checkLineup()`: at most five riders, all on the roster, each with a category, and the best and worst rank no more than three consecutive ranks apart. `POST /api/ladder/lineup` refuses an illegal line-up unless staff pass `force`. `suggest()` takes the strongest five by rating inside one window of three ranks among riders who have not said no. The page's line-up builder greys out riders who would break the rule as you pick.
- **Challenge and match.** `cg:ladder:matches`: opponent, who challenged (the challenger picks the route), route name, km and minutes, the UK date and time (stored as UTC), the private event link (https only, shown only to staff and riders on the roster), notes, status (`challenge`, `scheduled` once a time and link exist, `played`, `cancelled`), the line-up and the result. Riders on the roster answer yes, maybe or no per match (`cg:ladder:avail`).
- **Result.** `scoreMatch()`: the positions (1 to 10 in the race of ten) of our five give 10 points for 1st down to 1 for 10th; the other 55 − ours is theirs; the higher total wins. The record (played, won, lost, points for and against, and each rider's races, points, average and best finish) is derived from the played matches.
- **Notices.** `POST /api/ladder/post` sends the call for riders or the line-up with the private link to the ladder channel (`DISCORD_WEBHOOK_LADDER`, else the club channel; once per five minutes). `runSchedule` (cron tick, job "Ladder"): within three days with no legal line-up a warning goes to the admin channel; within a day of a scheduled match with a legal line-up the line-up and link are posted; two hours before, again; each once (`cg:ladder:sent`). A "Zwift Club Ladder" row in the health panel warns when a match within three days has no legal line-up.
- **Backups** now include the ladder keys, and the ride-cover keys that were missing.

## DIRT Racing Series (DRS)
`lib/drs.js` (factory `createDrs`, routes under `/api/drs/*`, `handleDrs`, a **🏜️ DIRT Series** tab). A structured league: one season at a time (`cg:drs:season`: name, division, the raw vELO `threshold`, `buffer` 35, `alertWithin` 10, `spikeLimit` 50, `squadMax` 8 (the club's DRS squad is eight; seasons already saved keep the size they were saved with), `scorers` 4, the slot name, the slot time and its time zone), a squad of eight (`cg:drs:squad`), a fixed calendar of stages (`cg:drs:stages`: scratch, points, itt or ttt, route, a private event link pulled from the DRS portal, the roles and the result), and a rating history (`cg:drs:ratings`).
- **Ratings** are the raw vELO numbers (`race.current.rating`) from the club roster the dashboard already caches, passed in as `getRatings`; the module makes **no ZwiftRacing.app calls of its own**, so the 5-a-minute and batch limits never come into play. This replaces the Google Apps Script idea: the same check, run by the scheduled tick, with the same "speak only when there is a problem" rule.
- **The buffer** (`buffer()`): before a rider's first race they must be at or below the threshold (`entry-over` otherwise, and `POST /api/drs/squad` refuses to nominate them unless forced); afterwards `ok` (at or below the threshold), `buffer` (above it, inside the 35), `danger` (within `alertWithin` of the cap, threshold + 35) or `breach` (past the cap: upgrade; a rise of more than 50 in one race that breaks it is a single-race DQ, flagged as a `spike` from the rating history).
- **Scoring** (`scoreStage`): staff enter each rider's position and the stage points the DRS results gave them; the four best-placed of ours score and their points are the team's. The plan (`POST /api/drs/roles`) names the scoring four (at most four; the suggestion is the four highest vELO); everyone else is support.
- **Schedule** (cron job "DIRT series"): each squad rider's rating is recorded when it changes; a single admin alert lists riders who are in the danger zone, past the cap, above the threshold before a first race, or who jumped by more than 50 (once a week per rider and state; once per jump); for each upcoming stage: a pre-check three days out if the squad is too small or someone is at the limit, a "finalise in the portal" reminder when the 24-hour lock is under 12 hours away, then the stage post a day and two hours before (route, time, private link, plan). A health row reports the division and any rider at the limit.
- The private event link is shown only to staff and squad riders. `POST /api/drs/reset` (admin, typed RESET) archives the season and clears the rest. Backups include the DRS keys.

The page builds each message in `public/index.html` (`waTttText`, `waZrlAllText`, `waZrlTeamText`, `waZrlOpenText`, `waZrlLineupText`, `waLadderText`, `waDrsText`, `waRideText`, `waCoverText`) and `waBtn(key, text, label)` renders two buttons: **WhatsApp** (opens `https://wa.me/?text=…` so staff pick the Community or group; a message too long for a link is copied instead) and **Copy**. Buttons sit on the TTT "More tools", ZRL Teams (all teams, sign-up call, each team, each line-up), Ladder matches, DIRT stages, social rides and the ride-cover panel. ## Low-touch automation (ZRL, TTT, Ladder, DIRT)
The aim is that a button either does the work or the app does it unprompted, and a person is only asked when a decision is really theirs. Every automatic step can be switched off, writes only what a person could have done by hand, and tells the admin channel what it did and what is left. The Captain 101 guides for the Ladder and DIRT describe how the leagues run; the rules below come from them.
- **ZRL one-click fixes** (`planFixes` / `autoFix` in `lib/zrl.js`, `POST /api/zrl/fix`, preview by default, `apply: true` to write, `only` to limit it to some of the readiness checks): place riders (`planAssignments`), move riders out of a class they are below to a team in their zone with room, give each team a captain (a volunteer, else the strongest rider with a Zwift ID, said so in the plan), set the race time from the league colour, and fill line-ups from the riders' answers (yes, then maybe, then not answered; never someone who said no). Nothing is ever taken off a team. What needs a person (no Zwift ID, no WTRL registration, a team too small, a league with no colour, a team that cannot field five) comes back as `left`. The readiness card has **Fix it** per check and **Fix everything I can**; applied runs are in the change log, previews are not.
- **ZRL automatic runs** (`round.autoFix = { place, lineups }`, both on unless switched off with `POST /api/zrl/auto-settings`): when sign-ups close, riders are placed and volunteer captains and league times set (never a rider moved, never a non-volunteer made captain), and the admin channel gets what was done and what is left; two days before a race, line-ups are filled from the answers (once per week, `…:autolineup`) before the existing nudge, which then names only the teams still short.
- **TTT automatic allocation** (`tttAllocation()` in `api/server.js`, shared by `POST /api/ttt/auto-assign` and the schedule): the preview now lists the captains it would pick. A team the plan leaves with fewer than four riders is dissolved into other started teams when every one of its riders was placed by that plan (nobody already settled moves). When sign-ups close the same allocation is applied (`week.autoAllocate`, on unless `POST /api/ttt/auto-settings`) and the admin post says what was placed, folded, short or without a captain. Publishing stays a person's decision.
- **Ladder** (`lib/ladder.js`): `suggest()` weighs the riders' answers (yes before maybe before no answer) and names a reserve from the same three-rank window; `autoPick()` also leaves out riders in another team's line-up at the same time. `POST /api/ladder/auto-lineup` saves the five and the reserve in one click. A starter (or the reserve) who answers no is replaced at once (`replaceStarter`: the reserve if legal, else the best legal rider; the admin channel is told, or warned when nobody fits). Per team `meta.auto` (default on) also lets the tick pick a legal line-up and reserve three days out instead of only warning. The tick also chases a challenge that still has no date or private link (the league wants it agreed five to seven days ahead), a match that has been run with no result (and reminds about the 24-hour protest window), and a team that has not raced for 14, 21 (zombie) and 30 days (removal is at 35). The page shows the challenge range from the rung (seven above), route guidance (15 to 25 km, 40 to 50 minutes), power-ups, one race a team a day (409 unless `force`), and riders who are on more than one ladder roster. Availability nudges now go out five days ahead (`pendingAnswers(now, 120)`).
- **DIRT** (`lib/drs.js`): squad riders answer yes/maybe/no per stage (`POST /api/drs/availability`, `cg:drs:avail`); `pickScorers()` chooses the scoring four from the answers, keeping anyone near or past the vELO cap out of the four (a big finish would force an upgrade) unless there is nobody else. `POST /api/drs/roles` with `auto: true` saves it. Five days out the squad is asked; at 72 hours the existing pre-check runs; two days out an audit post lists answers, buffer margins, single-race-DQ risk and whether fewer than four can race, and (season `autoRoles`, on unless `POST /api/drs/auto`) the four are picked; three hours after the start with no result the staff are reminded. The squad is locked into the season once a rider has started a stage and for the last 24 hours before a stage (409 unless `force`, for when Race Control has agreed). The squad size is eight, the stage post states the one-power-up rule and the no-height-or-weight-changes and HRM rules, and the single-race DQ needs both a rise of more than 50 and a rating past the cap. Squad riders who have not answered a stage within five days are in the Comms nudges (`drs.pendingAnswers`).

- **Results from ZwiftRacing.app** (`fetchZrResults` in `api/server.js`, one request a minute, the organizer key stays on the server). `POST /api/ladder/result-import` and `POST /api/drs/result-import` read the event named by the match or stage's private link (`/events/view/<id>`, or `event` in the request): preview first, `apply: true` to save. Ladder: the roster riders found in the event are the five who raced (the line-up is updated if the reserve rode), needing exactly five. DIRT: the squad riders found get their places; stage points still come from the DRS portal, so any entered by hand are kept. After a race starts the tick tries hourly for a day (`…:autores:<hour>`), saves the result, and tells the admin channel to check it; the "enter the result" reminder waits eight or nine hours when an import is possible.
- **Automation log** (`lib/autolog.js`, `cg:auto:log`, `GET /api/auto`, `POST /api/auto/undo`, admin and moderator): every automatic step records a summary and the commands that restore what it overwrote (ZRL fixes, TTT allocation, Ladder line-ups, replacements and results, DIRT roles and results). Only `HSET`, `HDEL`, `SET`, `DEL` on `cg:` keys are accepted. An entry is undone once. The This week page lists them with Undo.

They go only when the administrator has automatic messages on, the rider's Discord is linked and verified, and they have not turned the kind off; `key` makes each once.
- **Season records**: `POST /api/ladder/season-close` archives a team's roster, matches and record in `cg:ladder:archive` (optionally clearing the matches); `GET /api/ladder/archive`; `GET /api/drs/archive` lists and opens seasons archived by a reset or a team removal. `GET /api/profile` now carries `career` (ZRL rounds, TTT weeks, Ladder races/wins/points, DIRT stages/points) read from the live data and the archives.
- **Restore test** (`backup.verify`, weekly with the daily backup, `POST /api/admin/backup-verify`): the newest daily copy is unpacked and the commands a restore would run are built, nothing written; an unreadable, empty or far smaller copy fails and shows as a warning in the Backups health row.
- **Sheet mirrors for the Ladder and DIRT**: `ladder` and `drs` are sheet-sync series with `pull: null` (published to `CRYO-GEN App Ladder` / `CRYO-GEN App DIRT` in the ZRL workbook, or another chosen in Admin; the sheet cannot change the app yet, so they have no "pull"). They need the Google service account like the others.

### Phase 3 (race day, self-service, picks, forecasts, planner, digest, onboarding, public page, recognition)
- **Race day** (`lib/live.js`, `GET /api/live`, `POST /api/live/checkin`, cron job "Race day"): races starting from three hours ago to a day ahead (Ladder matches, DIRT stages, ZRL races with a race time) with the riders racing, their answers and whether they said they are **in the pen**. The app cannot see Zwift's pen, so that is the rider's own tap (My week, from an hour before to 45 minutes after a start) or a staff member's. `cg:live:checkins` is in the backups. Twenty minutes before a start, riders who are not in the pen and did not say no get one DM (`comms.notify`, once each). The staff card is at the top of This week and refreshes each minute.
- **Self-service**: My week now has Yes/Maybe/No for Ladder and DIRT as well as ZRL (`POST /api/ladder/availability`, `/api/drs/availability`). A Ladder starter who says no is replaced at once; a DIRT scorer who says no triggers a new pick of the four (when automatic roles are on), a DM to whoever comes in, and an automation-log entry.
- **Smarter picks**: the Ladder pick adds a small bonus or penalty for points a race in past matches (two races to count), the DIRT pick does the same with the average place in the same type of stage. Both explain themselves (ⓘ tooltip on the line-up and the plan, staff only).
- **DIRT forecast**: `forecastOf()` takes the rating history (60 days) to a points-a-week trend, a projection for the last stage still to come and the number of weekly stages until the cap; shown on the squad row, and a weekly early warning goes to the admin channel for riders heading for the cap who are not yet in the alert zone.
- **Challenge planner** (`GET /api/ladder/planner`): the rungs that may be challenged, whether a legal five exists, last race, the weekday riders say yes to most, three dates and times to propose (never a day the team already races) and a draft message. It cannot choose an opponent: other teams' standings are not known to the app.
- **Morning digest** (`runDigest`, `GET/POST /api/digest`, off until an administrator turns it on): once a day from 07:00 UK (`DIGEST_FROM_HOUR` exists for tests) to the admin channel: what needs attention, what is on today and tomorrow, and what the automation did, only when there is something to say. Discord only: the app has no email service.
- **Onboarding** (`lib/onboarding.js`, `GET /api/onboarding`): members first seen after the first run are tracked (the first run only records everyone already here); steps are a verified Discord link, a rider category, and a place in a series. Day 3 and day 10 DMs go to linked members with no team. Stuck members show on This week.
- **Public club page** (`public/club.html`, `GET /api/public/club`, `GET/POST /api/public/settings`): off until an administrator turns it on (404 until then). Shows Ladder records and recent results, DIRT tables, the ZRL round and team names, the next TTT, and next races: no rider names, ids, line-ups or private links.
- **Recognition**: `GET/POST /api/ladder|drs|ttt/recognition` and `post-recognition` build and post the end-of-season thank-you (record, top scorers, ever-present, firsts/podiums). The Ladder and DIRT accept an archived season's `id`. They are text posts: the app makes no images.

### Phase 4 (buttons, accounts, tables, no-shows, opponents, assistant, outlook, push, win-back)
- **Discord buttons** (`lib/discord-interactions.js`, `POST /api/discord/interactions`, `DISCORD_PUBLIC_KEY`): the availability reminders carry Yes / Maybe / No buttons (`custom_id` `av|<zrl|ladder|drs>|<id>|<answer>`). Discord posts each tap, signed with Ed25519 over the timestamp and the raw body; anything not signed by Discord is a 401. The tap is matched to a rider by their saved, usable Discord link and saved by the same route the dashboard uses (as that rider, with a member token made inside the process). Riders who cannot be identified get a private (flag 64) explanation. The portal's Interactions Endpoint URL must point at the route.
- **Staff accounts** (`lib/staff.js`, `cg:staff:users`, `/api/staff`): named administrator or moderator accounts with scrypt-hashed passwords; `POST /api/login` with `username` and `password` gives a session carrying `staffName`, which the change log uses instead of whatever the page sends. The shared role passwords keep working. A removed account stops working at the next sign-in; an open session lasts until it expires (12 hours). Password hashes are not in the backups.
- **Team captains** (Ladder `teamMeta.captains`, DIRT `season.captains`; `POST /api/ladder/captains`, `/api/drs/captains`, at most three, staff only): a captain (a member session) manages only that team's line-up and scoring four, answers for riders, posts and reads results (`needManage`). Creating matches or stages, rosters, seasons and settings stay staff only. Captains see the staff-level answers and reasons for their own team.
- **Results from a table** (`lib/csv.js`; `POST /api/zrl/results-import`, `POST /api/drs/points-import`; `apply` saves): columns are found by heading, our teams or riders are matched by name (or Zwift ID), other rows are ignored, and what the table does not carry (rider points, notes, places already read) is kept. ZRL applies the league-points rule when the number of teams started is given, and the change is in the automation log with an undo. Written without a real WTRL or DRS export, so an unusual layout may need a heading changed.
- **Race-day no-shows** (`lib/live.js`): ten minutes out, starters who are not in the pen are posted once to the admin channel and the bench (the Ladder reserve; DIRT support riders already in the pen) is asked to be ready; `POST /api/live/swap` puts one in (Ladder line-up, DIRT scoring four). It is the rider's own "in the pen" tap that the app sees, not Zwift's.
- **Ladder opponents** (`POST /api/ladder/standings`, `cg:ladder:standings`): the ladder table pasted in (rank, team, optionally last raced) sets our rung by name and lets the planner name opponents within seven rungs (zombies, 21+ days, skipped and not counted) and put the first in the draft. The app has no live feed of other clubs' teams.
- **Ask the club** (`lib/assistant.js`, `ANTHROPIC_API_KEY`): a model turns a request into at most five actions from a fixed menu (ZRL fixes, move a rider, set a captain, pick the next Ladder line-up or DIRT scoring four). Names are matched here, the plan is shown, and nothing runs until confirmed; changes go in the automation log with undo where there is one. The model only returns JSON; the data in its context is marked as data, not instructions. 60 requests a day.
- **Season outlook** (`GET /api/projection`): points per race (ZRL), per stage (DIRT) or the win rate (Ladder) carried over the races left, only once there are two results. Arithmetic, not a prediction model.
- **Web push** (`lib/webpush.js`, `VAPID_*`): RFC 8291 aes128gcm encryption and RFC 8292 VAPID signing with Node's crypto only, subscriptions kept per rider (five devices), gone devices (404/410) dropped. `comms.notify` and the automatic availability reminder fall back to push when a rider has no usable Discord, respecting their opt-outs; automatic messages can be switched on with push alone. The service worker shows the notification and opens the dashboard on a tap.
- **Win-back** (`lib/lifecycle.js`): active members 45 to 180 days since a race are listed on This week; with automatic messages on each gets one friendly message every 60 days (20 a day). Renewal reminders are not built: the member data has no expiry date.
- The hover helper's class is `rname` (it was briefly `rn`, which clashed with the ZRL results note field).

## Teams in the Ladder and the DIRT Series
Both series can have several teams (Ladder up to 15, DIRT up to 10); staff manage every team. Each team has its own roster of 15 (Ladder) or season, squad and calendar (DIRT) and its own record; a rider can be on several teams. Storage: `cg:ladder:teams` / `cg:drs:teams` (team id -> `{id, name, at}`; none stored means the one original team, `main`, named CRYO-GEN), roster and squad fields are `<team id>|<zwid>` (a plain zwid is read as `main`), matches and stages carry `team` (missing means `main`), the DIRT season is per team in `cg:drs:seasons` (the old `cg:drs:season` is `main`'s until it is next saved), and `cg:ladder:teammeta` holds each team's rung. Nothing is migrated: existing data keeps working as team `main`. Routes take `team` in the body (writes) or query (`GET /api/ladder?team=`); routes about one match or stage find its team from the id. `POST /api/ladder/team` and `/api/drs/team` add or rename (the first team added keeps `main`), `team-remove` deletes a team (Ladder needs `force` when it has matches; DIRT is admin only with typed REMOVE and archives the season). A rider asked for by two teams at the same time (within two hours) is flagged on the match/stage for staff and posted once to the admin channel; it never blocks. The reminders and posts name the team when there is more than one, the health rows cover every team, and This week and My week list every team's matches and stages (`ladder.allMatches`, `drs.allStages`).

## Comms (staff)
`lib/comms.js` (factory `createComms`, routes under `/api/comms/*`, a **💬 Comms** tab for admins and moderators). A staff message to Discord: **everyone** is one post in the club channel (`DISCORD_WEBHOOK_COMMS`, falling back to `DISCORD_WEBHOOK_PUBLIC`); **chosen members** (up to 50, also reachable from the Members selection with "Message them") are sent a direct message through the bot when `DISCORD_BOT_TOKEN` is set (open a DM channel, then post), and otherwise get one channel post that @mentions exactly those members. A member needs their Discord user ID saved (`cg:comms:discord`, zwid -> `{id, at}`, set by staff in Comms). Mentions are never taken from typed text: `allowed_mentions` lists only the chosen users, and `@everyone` is admin-only and explicit. Messages are signed "— CRYO-GEN staff", limited to ten sends a minute, and recorded in `cg:comms:log` (the last 100, no Discord IDs); results are reported per member (no ID saved, DMs closed, not attempted if the 7-second budget runs out) and failures stay selected so they can be retried. There is no bulk DM to everyone on purpose.
- **Riders link their own Discord** (My Profile, or Become a member for associates; `GET/POST /api/me/discord`, `/verify`, `/prefs`, `/remove`, `/test`). With the bot on, saving an ID sends a 6-digit code to that Discord account (15 minutes, five tries); only a verified ID is used by staff messages, and a verified account also ticks an associate's "Join our Discord" item. Without a bot there is nothing to verify with, so the entry is used as is (shown as "own ID, not verified"). A rider can switch the club's messages off (`dm: false`): staff sends skip them with the reason shown. Staff-entered IDs count as verified.
- **Kinds.** A rider can choose which kinds of message they get (race reminders, social ride messages, club news; `prefs` on the link, plus the master `dm` switch). Every send has a `kind` (a template sets its own; free text is club news) and skips members who turned it off, with the reason shown.
- **Sign in with Discord** (`DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET`, redirect `<SITE_URL>/api/discord/callback`): `GET /api/me/discord/start` returns the Discord authorise URL with a signed one-time `state` naming the rider; Discord sends them to `/api/discord/callback`, which checks the state, trades the code for the Discord user (scope `identify`), saves a verified link (`by: 'oauth'`) and redirects to `/#discord=linked|denied|expired|failed`. The code-by-DM flow remains for when it is not set up.
- **Automatic reminder** (off until an administrator turns it on in Comms; needs the bot): the scheduled tick DMs riders who have not answered for a ZRL race, Ladder match or DIRT stage starting within about five days (Ladder and DIRT; ZRL by its own window), once per rider per race (`cg:comms:sent`), only if linked, verified, not opted out and with race reminders on; capped at 40 a run and logged as sent by `auto`.
- **Ready-made reminders** (`lib/comms-templates.js`, `GET /api/comms/templates`): ZRL availability for the next race and captains with a short line-up, ZRL sign-ups open, TTT sign-ups, Ladder availability, DIRT stage coming up, associates ready to ask, and a call for everyone to add their Discord ID. Each lists the members it is for, worked out from the live data, and the words to send; staff review and press send. `{name}` and other `{words}` are filled in per member (`vars` in the send request); without a bot a personal message is one channel post each (at most 15). A template with too many people (over 50) becomes one club-channel post.

## My calendar (riders) and result posts (staff)
`lib/calendar.js` gives each signed-in rider a private iCalendar feed of their next four weeks (the same items as "My week": TTT, ZRL, rides they said yes to, ride cover, Ladder, DIRT Series; items still waiting for an answer are marked ❓ and TENTATIVE; "I can't" and un-RSVP'd rides are left out). The feed at `GET /api/cal/<secret>.ics` has no login: the 32-character random secret in the address is the key (`cg:cal:tokens` zwid → record, `cg:cal:owners` secret → zwid; both are in the backups). Responses are `private, max-age=900`; unknown or malformed secrets are a plain 404.

Result posts: `POST /api/ladder/post` and `POST /api/drs/post` accept `kind: 'result'` (409 until a result is saved; 5-minute duplicate guard like the other posts). The Ladder message gives the score and our five in finishing order; the DIRT message gives the team points and every finisher, with ⭐ on the riders whose points counted. After saving a result the page offers to post it, and each played match or stage has **Post result** and **Share result** (WhatsApp) buttons. ZRL already had **Post results** per race.

## ZRL team size and rider power
A ZRL team holds at most 10 racing riders (`requireRoom` in `lib/zrl.js`): the assign route and the rider edit refuse an eleventh with a 409 naming the team and its count; auto-assign already stopped at the size. The staff pages show each team's fill (7/10) in every team menu, grey out a full team, and replace the "add a rider" menu with a notice on a full team. ## Rider profile (staff)
A 👤 button beside a rider in Members and in the ZRL Riders tab opens a profile (`openRider` / `renderRider` in the page, not to be confused with the member's own `renderProfile`). The stats come from the club roster the page already holds: category, vELO with 30- and 90-day highs, FTP and estimated FTP w/kg, zMAP (5-minute w/kg), the power curve from 5 seconds to 20 minutes, rider type scores, course handicaps and the race record. `slimRider` now also keeps the watts at 5s, 1m, 5m and 20m, CP, AWC and the 30/90-day ratings; age, gender, height and weight are still dropped. `GET /api/profile?zwid=` (`lib/profile.js`, admin and moderator) adds the teams across ZRL, Ladder and DIRT Series, whether Discord is linked, and the staff details. `POST /api/profile` saves the staff details (time zone, preferred team, trainer, bike, a note, 800 characters at most), merged into `cg:rider:details` (included in the backups) with who and when; saves are logged. ## Import Discord IDs (Comms)
Comms → Import Discord IDs fills the Discord links in bulk. `GET /api/comms/discord-members` (admin and moderator) pages the server's member list through the bot (`DISCORD_GUILD_ID`, bots left out, 4000 members at most; a 403 means the Server Members Intent is off) and pairs each member with a rider; `POST /api/comms/discord-match` does the same for a list read from an uploaded CSV (the page finds the ID column and a name column). Pairing uses the club roster and WordPress names with tags like `[CRYO-GEN]` and accents removed: the same words score 100, the same first and last word 90, the same first word and last initial 70, and a first name alone nothing. A single best 90+ match is `exact` and pre-selected, anything else is `near` (staff choose) or `none` (staff can search a rider). Nothing is saved until staff confirm: `POST /api/comms/import` saves the chosen pairs as staff links (`by: 'staff'`, usable for messages), skips a rider who linked themselves, and reports what it skipped. Riders who later use Connect with Discord replace the imported link with a verified one.

Size: the two big routes (`/api/comms/import`, `/api/comms/discord-match`) read a body of up to 800 KB, after the staff check; every other route keeps the 20 KB limit. A match takes up to 5000 members and a save up to 1000 links per request (the page saves in batches of 300), written in a few Redis round trips. Two Discord members that match one rider are held back as conflicts (neither pre-selected) and the page will not save a rider chosen twice; the server also skips a Discord member chosen for two riders.

## Time zone preference
Times in the page follow the viewer's zone: `tzZone()` is their device's zone or one they pick (🕒 button in the header → `openTz`), `tzAlso` adds UTC beside key times (`tzUtcSuffix`), and `slotLocal()` converts a league's fixed "Tue 18:00 UTC" for its next occurrence in the viewer's zone, so summer and winter time come out right (shown raw when the viewer's zone is UTC). The choice is kept in `localStorage` (`cgTz`, `cgTzUtc`); for a signed-in rider (members and associates) it is also saved on the server (`GET/POST /api/me/tz` in `lib/profile.js`, hash `cg:me:tz`, in the backups) and loaded after sign-in, so it follows them to other devices. Zone names are checked with `Intl.DateTimeFormat` (`device` is accepted and means follow the device). Race, ride, cover, Ladder and DIRT times, This week and My week, sign-up closing times and the staff change log use it. What stays as authored: the shared WhatsApp text (UK time), the editors where staff type a date and time (UK time), and the cover series zone.

## The club's Google Sheet (TTT)
The workbook has the Google Form responses on its first tab and the published teams on `TEAM LIST`. **Sign-ups** (`POST /api/ttt/import-sheet`, preview then apply) are read from the form tab, found by `SHEET_TAB_TTT_FORM`, then `Form Responses 1`, then the workbook's first tab, and accepted only if the tab has the form's columns: the name from "Please select your name" (or the *OTHER* answer), the Zwift ID from the "Zwift Power ID Number" answer (else matched to the club roster by name), `Availability` (not the zones question), the level for the week, double-up, the region, and the teams asked for (turned into the rider's preferred teams). Emails never leave the server. **The published teams** (`POST /api/ttt/import-board`) are read from the `TEAM LIST` tab by `readTeamBoard`: each block starts at a `(CRYO-GEN Name)` tag cell (zone above, pen below), the riders' names run down that column and a Zwift ID may sit in the column to the right; riders without an ID beside them are matched to the club roster by name, and without tag cells the reader falls back to columns of Zwift IDs with names beside them. The preview lists the columns it read and, for every rider, whether the app already agrees (`same`), can place them (`unplaced`, `new`), has them on another team (`elsewhere`, moved only with `overwrite`) or the block has no matching team here (`no-team`). Applying creates missing sign-ups and places unplaced riders on the named team, never past the team size. This is a one-way read (sheet to app); nothing is written to the sheet.

## Duplicate and inactive members
`GET /api/members/tidy` (`lib/tidy.js`, admin and moderator) reads the raw WordPress member list and the club roster and reports: the same name (tags, brackets and punctuation ignored) under more than one Zwift ID, with a suggested record to keep (in the club, active, full member, raced lately); Zwift IDs WordPress holds twice, and records with no usable Zwift ID (neither can be managed through the app, which finds a record by its Zwift ID, so they are listed to fix on the website); and active members who are not in the Zwift club (associates excepted), have never raced, or have not raced for a chosen number of days (`race.last.date` from the club data). The page (Members → 🧹 Duplicates & inactive) acts with the existing member save: mark as left or suspend, singly or in bulk (up to 100), or message them from Comms.

## Google Sheet sync (TTT and ZRL)
The club runs its sheets and the app side by side, so `lib/sheetsync.js` keeps them in step in two directions per series. **Sheet to app (pull; the sheet wins):** TTT reads the sign-up form tab and the published teams on `TEAM LIST` (`import-sheet`, then `import-board` with `overwrite` and `prune`: riders are placed as the sheet has them and a rider the sheet no longer lists comes off that team); ZRL calls `POST /api/zrl/sync-board`, a gentler import than the full one: for teams the app already has, a rider on the sheet is placed (a missing sign-up is created) and a rider the app has there but the sheet does not is taken off, while captains, race times and teams only one side has are left alone (teams only the sheet has are reported, and a sheet that matches none of the app's teams changes nothing). **App to sheet (push):** the app writes its teams to a mirror tab it owns (`CRYO-GEN App TTT`, `CRYO-GEN App ZRL`), replaced each time and skipped when nothing changed; the club's own tabs are never written. Writing uses a Google service account (`lib/gsheets.js`: a signed JWT exchanged for a token, then the Sheets API; the key is only ever sent to Google) that each sheet has been shared with as an Editor.

Everything is off until an administrator ticks it in Admin → Google Sheet sync (`GET/POST /api/sync`, `/api/sync/settings`, `/api/sync/run`, `/api/sync/auto`). A run never overlaps another (a Redis lock per series), a failure in one direction is recorded and does not stop the other, and the state (last run, rows, errors) shows on the card and in the health checks. Runs happen on every scheduled tick (the GitHub Action calls it every 15 minutes) and, at most every ten minutes, when staff open the TTT or ZRL page. The ZRL sheet defaults to the club's ZRL tracker (`ZRL_SHEET_ID`, or changed in Admin). The Ladder and the DIRT Series are published to mirror tabs only (no pull until their sheet layouts are known).

## Associate members
`lib/assoc.js` (factory `createAssoc`, routes under `/api/assoc/*`, `handleAssoc`, a **⬆️ Become a member** tab, a staff **Associates** panel in Members). A second level of sign-in: someone who signs in with cryogen.team but is not yet a full member gets a limited session (`assoc: true` in the signed member token) and a route to full membership.
- **Half = associate.** They are one membership. `normTier` in `api/server.js` reads a WordPress `half` as `associate` (roster view, `/api/me`), `classify` treats both as associate, and the tier menus offer only Full and Associate (`half` from an older caller is saved as `associate`). WordPress records that still say half keep their value there until staff next change them; the app never shows it.
- **Who is an associate** (`classify`, decided at SSO with a fresh roster look-up): staff approval always wins (`cg:assoc:full`); a staff mark (`cg:assoc:marks`) makes one; a WordPress record decides next (tier `associate` or status `pending` is an associate, any other tier is a member); with no record, someone already seen as an associate stays one until approved, and otherwise not being on the club roster means associate.
- **What they can call**: the `ASSOCIATE_ALLOWED` list in `api/server.js` (TTT and ZRL sign-up, other race sign-ups, social-ride RSVPs, what the pages read, their own `/api/assoc/*`). Everything else under `/api/` answers 403 with `associate: true`. The gate re-checks `stillAssociate` on every call, so an approval unlocks a live session at once.
- **The checklist** (`progress`): in the club on Zwift, joined Discord (self-ticked), `RULES.rsvps` social rides, one team event, `RULES.days` days since first seen. When complete they can request; staff are told on the admin channel. Staff can approve anyone at any time (`approve` also sets the WordPress tier to full when there is a record), or decline with a note.
- **Schedule** (cron job "Associates"): a weekly admin digest of requests waiting more than three days and associates ready to ask. A health row reports the pipeline. Backups include the assoc keys.

## Fair play (staff only)
- `lib/fairplay.js`, page "🔎 Fair play" (admin and moderators). A daily scheduled job takes one snapshot per active rider (registered weight, 5 and 20 minute W/kg, vELO) and flags: a weight drop of more than 2 kg in 7 days (or an implausible weight), a 5 or 20 minute W/kg more than 5% above their best of the previous 90 days (needs four readings older than two weeks), and a vELO rise of 150 or more in 14 days. Severity 1 to 3 by size.
- A flag is a prompt for a person, never a finding. Staff mark each one Fine, Confirmed or Dismissed with a note; a dismissed item is not raised again unless it gets clearly worse or a month passes. Nothing is sent to the rider, members cannot read it, and the admin channel only gets a count.
- Registered weight is written to a private key (`cg:fair:weights`) when the roster is fetched and is not part of the roster members can fetch.
- Not checked, because the data the club receives has no heart rate or second-by-second power: heart-rate decoupling and "sticky watts". Adding them needs FIT files or a stream source.

## Investigation files and the AI coach
- **FIT reader** (`public/js/fit.js`): a small decoder that runs in the browser (and in Node for the tests). A ride's file is read on the rider's or staff member's own device; only the recorded numbers (time, power, heart rate, cadence, speed, distance, altitude, the devices that recorded it) are sent. No locations are read.
- **Analysis** (`lib/fitanalysis.js`): describes one ride: best efforts, NP, heart rate (missing in the hardest effort, flat while power moves, not following power), flat or "sticky" power, unusually smooth minutes, power dropping to zero while pedalling, impossible spikes, and what the climbs say the rider weighs (power / (speed x gravity x grade), compared with the registered weight). Every finding has a severity and the ordinary explanations beside it. Weight-dependent parts (`weightFindings`, `reweigh`) re-run from the stored numbers when a weight is corrected.
- **Investigations** (`lib/investigations.js`, page "🕵️ Investigations", admin and moderators; delete is admin only): a case per rider with notes, up to 12 files, cross-ride comparison and history. Only the worked-out numbers and a thin 10-second chart line are stored, not the second-by-second data. The optional AI summary (`POST /api/inv/ai`, 30 a day) receives the numbers and staff notes, never the rider's name or ID, and is told it is an analyst not a judge. A "🕵️ Investigate" button on each Fair play item opens a case.
- **Coach** (`lib/coach.js`, page "🧠 AI Coach", signed-in full members): needs `ANTHROPIC_API_KEY`, a one-time yes from the rider (revocable), 12 questions per rider per day and 400 a day overall. The model sees the rider's roster numbers (category, FTP, best W/kg, vELO, the week's events), never name, weight or contact details. Conversations are not stored: the browser sends the last few turns. "Explain my ride" analyses a FIT file in memory and returns pacing, zones and heart-rate drift; no fair-play findings reach the coach. `COACH_MODEL` and `INVESTIGATION_MODEL` can override the model.
- Uploads of whole rides (`/api/inv/file`, `/api/coach/ride`) may be up to 3 MB; everything else keeps the 20 KB limit.

## Supporters, limits and AI cost (lib/support.js)
- The coach is the only part with a cost per use, so it has two tiers. **Free:** 3 questions a week and one ride explained a month. **Supporter:** up to 15 questions a day and any number of rides, and a ⭐ next to their name for other members. All numbers are settings in Admin → ⭐ Supporters and AI cost.
- The app takes no payments. A rider pays through the club's own link (Ko-fi, Stripe, bank transfer; the link is a setting) and an administrator adds them as a supporter by hand, optionally until a date. Everything else in the app stays free.
- **Cost:** every AI answer's tokens are counted per day (`cg:ai:usage`). With the club's per-million-token prices entered, Admin shows the month's cost; an optional **monthly budget** rests the free coach when it is reached, and rests it for everyone at one and a half times the budget, until next month. With "show members the cost" on, the coach page tells members what the coach has cost and what supporters give.
- A coach answer that fails gives the question back. The question text is never stored.

## The AI suite (lib/ai.js, lib/aiplans.js, lib/aistaff.js, parts of lib/coach.js)
- **`lib/ai.js`** is the shared door to the model for the newer features: the key, the model (`AI_MODEL`, else `COACH_MODEL`, else the assistant's), the monthly budget (from `lib/support.js`), an optional daily cap per kind of use across the club, token counting, and the answer joined from every text block. Scheduled jobs ask `ai.available()` first and quietly skip when the AI is off or the budget is used.
- **Weekly plan** (supporters who said yes to the coach and opted in): queued on Monday from 06:00 UTC and worked through a few riders per scheduled run (Tuesday finishes a long queue); sent as the club's automatic message (kind "coaching plans and briefings", which riders can switch off) and kept to read on the coach page.
- **Race-day briefing**: about an hour before a Ladder, DIRT or ZRL race, one model call for the whole line-up (riders are "A", "B", … so no names go out), sent once to the riders who said yes to the coach, each with their own tip.
- **Coach extras**: "Ask about the club" (answers only from the club's own results, teams and fixtures plus the asker's own week), "My season story", and a **race debrief** mode for a FIT file. All count as coach questions, and a failed call gives the question back.
- **Staff**: a second opinion on a ZRL line-up (staff or that team's captain; swaps are checked against the real answers and never applied), a weekly report written Monday from 07:00 UTC (counts and titles only; posted to the admin channel; plain-text fallback when the AI is off), a kind draft for riders on the quiet list (first name put back by the club, never sent for you), and the club's story.
- Not built: asking the coach from inside Discord. A model answer takes longer than the three seconds Discord allows for a reply, and the hosting does not keep running after the reply is sent, so it cannot be done reliably here. Plans and briefings are delivered by Discord direct message or notification instead.
