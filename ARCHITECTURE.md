# Architecture

```
Browser (public/index.html)
 ├─ fetch /api/roster, POST /api/members/{zwiftId}       → api/server.js → WordPress plugin on Hostinger
 │     /members                     member records (tier, status, offboarding), read + PATCH
 │     /zwift/public/clubs/2740/0   live roster from ZwiftRacing.app
 ├─ fetch /api/proxy?endpoint=rides|ttt-sheet           → api/server.js → Google Sheets (gviz JSON)
 ├─ fetch /api/state, POST /api/signups|rsvps|rides|…   → api/server.js → Upstash Redis (shared)
 └─ localStorage                                         affiliation history (per browser)
```

## Frontend (`public/index.html`)

A single file with no build step. Tabs: Team Overview, Racing Dashboard, Events & Sign-Up, Social Rides, Members, plus a profile page.

- **Roles:** admin, moderator and member. Admin and moderator passwords are checked by `POST /api/login` against the `ADMIN_PASSWORD` / `MOD_PASSWORD` environment variables. Members either sign in with their cryogen.team account (verified) or pick themselves from the live roster by name or Zwift ID (guest). The role is kept in `sessionStorage`.
- **Data loading:** `loadLive()` reads `/api/roster`, which merges the club roster with the WordPress member records by Zwift ID. If loading fails, it falls back to a small `MOCK` roster.
- **Member edits:** tier, status and off-boarding checkboxes call `POST /api/members/{zwiftId}` (staff only). The server PATCHes the WordPress record, reads it back, and reports an error if a field didn't save. The browser never holds WordPress credentials.
- **Shared state:** sign-ups, series locks, club-created rides and RSVPs come from `/api/state`. Every write returns the full new state, which the page re-renders from.
- **Escaping:** everything people type is shown to other people, so it's rendered through `esc()`. Values passed to click handlers go through `data-*` attributes, never inline into the JS.
- **Local state:** affiliation history is still saved to `localStorage`.

## Proxy (`api/server.js`)

A plain Node.js request handler:

- `POST /api/login` with `{role, password}` checks the role's password environment variable. It returns `{role, token}` on success (an HMAC-signed token, valid 12 hours), 401 on a wrong password, and 503 if the variable isn't set.
- `GET /api/proxy?endpoint=rides|ttt-sheet` reads that tab of the Google Sheet and returns `{rides, headers, updated}` or `{headers, rows, updated}`. Dates become `YYYY-MM-DD`. Only the named tabs are allowed.
- Shared data, stored in Upstash Redis hashes `cg:signups`, `cg:locks`, `cg:rides` and `cg:rsvps`:

  | Route | Who |
  |---|---|
  | `GET /api/state` | anyone |
  | `POST /api/signups`, `/api/rsvps`, `/api/rsvps/cancel` | anyone |
  | `POST /api/signups/remove`, `/api/rides`, `/api/rides/remove` | admin or mod (Bearer token) |
  | `POST /api/signups/clear`, `/api/locks` | admin |

- TTT week (Redis `cg:ttt:week`, `cg:ttt:signups`, `cg:ttt:assign`, `cg:ttt:archive`). Responses depend on the caller: comments are staff-only, and line-ups are hidden from members until published.

  | Route | Who |
  |---|---|
  | `GET /api/ttt`, `GET /api/ttt/archive?id=<date>` | anyone |
  | `POST /api/ttt/signup` (sign up or update), `/api/ttt/withdraw` | anyone, while sign-ups are open |
  | `POST /api/ttt/assign`, `/api/ttt/auto-assign`, `/api/ttt/status` (open/publish), `/api/ttt/teams`, `/api/ttt/new-week` | admin or mod |

  Starting a new week archives the current one with its line-ups and carries the teams over. Auto-assign places available, unplaced riders into their preferred teams (two for double-up), earliest sign-ups first, up to each team's max.

- When run locally, all other paths serve files from `public/`.

The file exports its handler for Vercel. `vercel.json` rewrites `/api/*` to it, and `npm start` runs it as a local server.

## Club roster cache

The roster comes from ZwiftRacing.app through the WordPress plugin, which answers 429 when asked too often. Each server instance used to ask on its own. The slimmed rider list is now kept in Redis (`cg:roster:riders`): reused for 10 minutes by every instance, and the last good copy is served if the source fails. Member records are not cached there; they are read each time the 5-minute in-memory cache expires.

**One rider, one sign-up.** TTT sign-ups are keyed by the lower-cased name, so the same rider could end up twice (a guest and a signed-in sign-up, or two spellings). Guest names have their spacing collapsed; a sign-up whose Zwift ID is already on the week updates that sign-up (keeping its name, queue place and team places); withdrawing removes every sign-up carrying the rider's Zwift ID; My TTT finds the sign-up by Zwift ID; and `mergeDuplicateSignups` merges any existing duplicates whenever the TTT page loads (earliest name and place kept, latest answers win, team places combined up to 2, a captaincy follows).

## TTT Season page

`GET /api/ttt/season` (public) feeds the **TTT Season** tab. `seasonSummary()` reads up to the latest 60 archived weeks, plus the current week once it has results, and returns totals, per-team stats (weeks, best and average place, podiums, DNFs), a rider leaderboard (weeks ridden, times captain, podiums; top 25) and a week-by-week list. A team counts for a week only if it had riders or a result. It uses only names, line-ups, captains and results, never comments or Zwift IDs. 

**Seasons.** A season is a name and a start date (Redis `cg:ttt:seasons`, JSON `[{id: <start date>, name, start}]`); it runs until the next season starts. `GET /api/ttt/season?season=<id>` returns that season's summary plus the list of seasons to choose from; the default is the latest. Until the first season is defined there is a single "All weeks" entry (the old behaviour), and once one exists, weeks before it appear as "Earlier weeks". Staff (admin or moderator) add a season with `POST /api/ttt/seasons {name, start}` (must start after the latest) and remove one with `POST /api/ttt/seasons/remove {id}`, whose weeks then fall back into the season before it. Nothing is ever deleted: seasons only decide which archived weeks the page shows.

## ZRL round sign-up

Logic lives in `lib/zrl.js` (a factory that `api/server.js` wires up; not in `api/`, since every file there becomes a public function). Redis keys: `cg:zrl:round` (name, start, closes, weeks, open, published, teams), `cg:zrl:signups` (one field per rider), `cg:zrl:assign`, `cg:zrl:archive`, `cg:zrl:sent`. Regions are `eu`, `am`, `ap` (Asia-Pacific).

- `GET /api/zrl` is public: the round, the demand per region (riders, teams, places still to fill) and the sign-up pool. Comments, Zwift IDs and preferred team are staff-only.
- `POST /api/zrl/signup` and `/withdraw` use `identify`, so a signed-in member can only sign themselves up. At least one time zone is required when racing; category defaults to the rider's profile category.
- Staff only: `POST /api/zrl/round` (starts a round, archives the previous one, keeps the teams, posts "sign-ups open" to Discord), `/status` (open or closed, published) and `/teams` (replace the team list).
- `POST /api/zrl/import {tab, apply, regions}` (staff) reads the team board tab of the club Google Sheet: one block of columns per team (zone or colour label, name, "Division n", grade, a Rider header row, one rider per row; blocks differ in width). Without `apply` it returns a preview; with it, teams and rosters (`cg:zrl:assign`) are replaced and riders without a sign-up get one. Missing Zwift IDs are filled from the club roster by exact name. The board's EMEA/AMERICAS labels give a time zone; colours do not, so staff pick those. Teams may carry `division` and `grade`.
- `POST /api/zrl/import-signups {tab, sheet, apply}` (staff) reads the form responses tab (one row per submission): Zwift ID from the ZwiftPower link, else a bare number, else the club roster by name; the latest row per rider wins. Time zones come from the primary and backup league labels (words like EMEA/Americas, else the UTC race time read as a local evening, else the colour). A rider's own sign-up on the page is never overwritten; sheet-made entries (`source: 'sheet'`) are refreshed. Staff also see the league, commitment (`commit`), previous team (`prevTeam`) and `source`. Sheet tabs are read with `fetchGrid`, which cannot tell an unknown tab name from the first tab (Google answers both the same), so each importer checks the layout it expects.
- `POST /api/zrl/auto-assign {apply}` (staff) suggests, or with `apply` makes, a team for every rider racing who has none (`planAssignments`, a pure function). Rules: a rider may ride their own category or a weaker one (team category = the last letter of its grade); the team must be in one of the rider's time zones and have a free place (10); full-season riders before reserves, those who named a team first, then first come; each goes to the eligible team nearest to full so teams complete, a close category match breaking ties; a captain-minded rider becomes the captain of a team that has none. Riders who cannot be placed are listed with the reason. `POST /api/zrl/assign {key, team}` (staff) moves one rider, or takes them off with an empty team.\n- `GET /api/zrl/export` (staff) builds the registration list for WTRL (which has no public sign-up, so captains register by hand): per team a readable block (name, division, grade, time zone, captain, numbered riders with Zwift ID and category), a plain list of Zwift IDs, the problems (no captain, not 10 riders, missing IDs or categories), riders with no team, and one CSV. CSV cells that start with `=`, `+`, `-` or `@` are prefixed with an apostrophe so a name can never run as a spreadsheet formula.\n- `GET /api/zrl/mine` (signed-in member) is the rider's own view: their sign-up, their team once `published` (names and categories only), and, if they are a team's captain, that team straight away with Zwift IDs, the registration text and the problems to sort out (`myZrl`). Comments, other teams and other riders' IDs never appear. The ZRL page shows it above the sign-up card.\n- Publishing (`POST /api/zrl/status {published: true}`, with a 📣 Publish rosters button in the staff panel) lets riders see their team and, the first time per round (claimed in `cg:zrl:sent` as `<round id>:published`), posts "the rosters are out" to the club channel (counts per time zone, where to look; no rider names) and a to-do list to the admin channel (teams without a captain or short of riders, riders without an ID or team). `announce: false` publishes silently and does not use up the announcement.\n- WTRL fixes each league's race time by its colour (not by division or men/women). `LEAGUE_ANCHORS` in `lib/zrl.js` holds, per colour, the city and local time it is anchored to (the violet cell of the 2026/27 league table); `leagueSlot(label, start)` turns that into `Tue HH:MM UTC` for the round's first race day, so daylight saving is followed. Every team in `GET /api/zrl` carries it as `wtrlSlot`, the Setup tab shows it beside each league with a ✓ or amber, and `POST /api/zrl/league-times` (staff) applies it to every team whose league names a colour, leaving other teams alone.
- Weekly management, per race week (`round.weeks`, a week every 7 days from the first race; `weekDate`). Stored in the hash `cg:zrl:weekly`: `a:<week>:<zwid>` is a rider's answer (`yes`, `maybe`, `no`) and `l:<week>:<team id>` is the JSON list of Zwift IDs the captain picked. It is cleared when the next round starts (the old answers go into the archive snapshot). `POST /api/zrl/availability {week, status, zwid?}` (a rider for themselves, a captain for their own team's riders, or staff; the rider must be on a team; an empty status clears it). `POST /api/zrl/lineup {week, team, zwids}` (the team's captain or staff; only riders on that team with a Zwift ID, at most `round.racing` of them, nobody who said no; an empty list clears it). `GET /api/zrl/mine` carries each rider's `weeks` (own answer, whether picked, the line-up names) and, for a captain, per team per week the line-up and every rider's answer. `GET /api/zrl` carries the raw `weekly` answers and line-ups for staff only, which the staff team panel uses to edit a team's line-ups and each rider's answer (same routes as the captain, no captain login needed). `GET /api/zrl/weekly` (staff) is the overview behind the 📅 Weeks tab (line-up size and yes/maybe/no counts per team and race). The ZRL health row warns when the next race is within three days and teams have not picked a full line-up (`healthRow` takes the weekly data as `data.weekly`).
- Race-week reminders run in `zrl.runSchedule` (the same tick as the sign-up reminder and close), once the rosters are published, per race week and only until the race day starts (00:00 UTC on that date): five days before, the club channel asks riders whether they can race (`<round id>:w<i>:avail` in `cg:zrl:sent`); two days before, the ZRL admin channel lists the teams that have riders but no full line-up (`:w<i>:lineup`; nothing is posted, and the claim is kept, when every team is sorted). A scheduler that was down catches up: a reminder whose time has passed fires once if the race has not started.
- WTRL registration tracker. WTRL has no API, so captains register by hand and say so: `POST /api/zrl/wtrl-registered {team, registered}` (the team's captain or staff; `registered: false` takes it off) stores `r:<team id>` in `cg:zrl:weekly` (so it clears with the round). Staff set the deadline with `POST /api/zrl/wtrl-deadline {date}` (stored as `round.wtrlDeadline`, 23:00 UK on that day; empty removes it). Teams in `GET /api/zrl` carry `wtrlRegistered`; the captain view carries `registered` and the round's deadline. The health row counts teams with riders that are not registered once a deadline is set, and `runSchedule` posts the list to the ZRL admin channel once, three days before the deadline (`<round id>:wtrl3`; nothing if all are registered). `load()` now returns `weekly` as well.
- Rollover: `POST /api/zrl/round {name, start, closes, weeks, carryRiders}` archives the current round (teams, sign-ups, placements and the weekly answers) and starts the next. Teams always carry over, with race times recalculated from the league colour for the new dates (`leagueSlot`, empty when the league names no colour) and `captainLocked` reset. Without `carryRiders` captains are cleared and the round starts with no riders. With `carryRiders: true` every rider who is in and on a team is copied (marked `carried`, original sign-up time kept) onto the same team, and a captain who is among them stays captain. The option is ignored when there is no earlier round. The Setup tab's "Start a new round" card has the tick-box (on by default) and a confirm that says how many riders stay.
- Change log. Every successful `POST` to a ZRL route is recorded by `logChange` (called from `handleZrl`) as a short entry, newest first, in the capped list `cg:zrl:log` (500 kept): time, role (`admin`, `mod`, `member` or `guest`), the member's name when there is one, the route, and a description built only from a whitelist of fields (team, week, status, name, key, zwid and the like; lists are counted, never copied; anything named like a password, token or secret is skipped). Requests that are refused are not logged. `GET /api/zrl/log` (staff) returns the latest 100, shown in the Setup tab under Recent changes.
- Results and standings. Staff record, per race week and team, the finishing position and the points scored: `POST /api/zrl/results {week, rows:[{team, pos, pts, note}]}` (staff; positions are whole numbers from 1, points numbers from 0, blank clears a row; the note is staff-only) stored in `cg:zrl:results` (`<week>:<team id>` -> `{pos, pts, note}`). `GET /api/zrl/standings` (open to everyone) groups the teams that have a result by their division (or league, or "All teams") and ranks them by total points, then best finish, with ties sharing a rank (`standingsOf`); staff also get the raw `entries` for the entry form. The ZRL page shows the standings card to riders and the staff 🏆 Results tab has the entry grid per race. Starting the next round archives the results with the round (`snapshot.results`) and clears them.
- Subs finder: `GET /api/zrl/subs?team=<id>&week=<n>` (the team's captain or staff) returns how many are picked for that race and how many more are needed, the bench (the team's own riders with a Zwift ID who are not in the line-up and did not say no, yes before maybe before no answer) and a pool of racing riders with no team who are in the team's time zone and whose category may ride it (same `catGap` rule as auto-assign; staff also get each rider's `key`). `rosterFull` is true when the team already has the full roster. In the page it is the 🔎 Find subs button under each race of the line-up editor; staff get an Add to team button (the existing assign route), captains are told to ask the staff. Zrl routes now receive the query string as a third argument.
- Past rounds (staff, Setup tab → Past rounds). `GET /api/zrl/archive` lists the archived rounds (name, first race, teams, riders) and `?id=<round id>` returns one: teams with captain and riders, and its standings with the raw result entries. `POST /api/zrl/archive-edit {id, name?, week?, rows?}` renames it and/or corrects its results (the same validation as live results, `resultEdits`). `POST /api/zrl/archive-delete {id}` (admin only) removes it. `POST /api/zrl/round-delete {confirm}` (admin only; `confirm` must be the current round's first-race date) deletes the current round and everything stored for it (sign-ups, placements, weekly answers, results and its scheduled-post marks), for a test round started by mistake. Past rounds' sign-ups and placements are not editable, only the name and the results.
- `POST /api/zrl/round-edit {name, start, closes, weeks}` (staff) corrects a round's name and dates in place (the id follows the first-race date): sign-ups, teams and placements stay, nothing is announced, and the reminder and close events for the old and new date are cleared so they fire on the new dates. Refused if an archived round already started that day.\n- `POST /api/zrl/signup-edit` and `/signup-remove` (staff) are the override: add a rider (with or without a Zwift ID), change any detail of any sign-up (racing or not, time zones, category, commitment, captain, preferred team, comments, team), or correct a name or Zwift ID, which moves the sign-up and its team place. Edits are marked `source: 'staff'` and `edited`, and the sheet import never overwrites a sign-up that has any source other than `sheet` (riders' own sign-ups carry none and are protected too). The ZRL page shows a ✏️ button on every row (including riders who are not racing) and a + Add a rider button.\n- Captains are automatic: after every `POST` to a ZRL route (an import, a move, a rider ticking the star) `afterChange` gives each team that has riders and no captain its first volunteer (the earliest sign-up with the star and a Zwift ID; the auto-assign preview uses the same rule). A captain is never replaced, and one that staff cleared by hand (`captainLocked`, set when the choice is emptied here or the ID is cleared in the team editor, unset when a captain is chosen) is not put back. `POST /api/zrl/captain {team, key}` (staff) chooses a team's captain from its own riders (must be on that team and have a Zwift ID; an empty key clears it). `POST /api/zrl/captains {picks:[{team,key}]}` (staff) does the same for several teams at once, all or nothing; the Teams tab shows a "Teams without a captain" card with a drop-down per team, a Suggest button (volunteers first, then earliest sign-up) and Save captains. Other volunteers in a team that already has a captain are listed as spare on the Rosters and captains card, with a drop-down to move them to a team that has none, where they become its captain.

## System health

`GET /api/health` (admin only) powers the **System health** section of the Admin dialog. It reports status (ok / warn / fail / info) for shared storage, WordPress member records, the club roster copy, the Google Sheet, Discord webhook configuration, the TTT week (including a missing close time), the ZRL round (`healthRow` in `lib/zrl.js`: sign-ups open or closed, riders per time zone, teams and placements, and warnings for no close date, a close time that has passed, rosters unpublished within a week of the first race, riders without a team, and, once sign-ups are closed or the rosters are published, teams that have riders but no captain or no race time; several problems are listed together), scheduled runs, member sign-in, guest sign-ups, staff passwords and the deployed commit. It only reports whether things are set and reachable, never values. It does not post to Discord or call the rate-limited roster source. The workflow's last run comes from `cg:cron:last`, written by every `/api/cron/tick`. The Google Sheet check makes two short tries (3.5 s each, inside the check's own 8 s limit) and records the last good answer in `cg:health:sheet-ok`; if Google times out twice but answered within the last 24 hours it shows a warning ("slow to answer right now") instead of a failure, and an unreachable Google or a first-ever timeout is still a failure.

**Expired staff logins.** A staff token lasts 12 hours. The page wraps `fetch` once: when a staff request (role admin or mod) is answered 401 with "Please log in again", it clears the session, flags `expired` in `sessionStorage` and reloads, and the login screen then says "Your session has expired. Please log in again." (once). Members and guests are not affected. `test/session-expiry.test.js` guards the wording the page looks for.

## Member sign-in

Riders can sign in with their cryogen.team account instead of picking a name.

1. The "Sign in" button goes to `WP_SSO_LOGIN_URL` on WordPress. A snippet there logs the member in if needed, then redirects to `/api/auth/wp?t=<token>`.
2. The token is `base64url(JSON {zwid, name, exp, n}) + "." + base64url(HMAC-SHA256(WP_SSO_SECRET, first part))`. It must expire within 10 minutes and can be used once (nonce stored in Redis as `cg:sso:<n>`).
3. The server issues a 12-hour member session (same signing as staff sessions, `role: "member"`, with `zwid` and the roster name) and redirects to `/#sso=<session>`. The page reads the fragment, stores the token and removes it from the URL. Members whose WordPress record is `left` are refused.
4. With a member session, `identify()` forces the sign-up, withdrawal and RSVP routes to act as that rider whatever the request body says. A member session is never a staff role.
5. Guests (name-picker) can still write until `REQUIRE_MEMBER_LOGIN=1`; then they get a 401 asking them to sign in. Staff can still act for others.

`GET /api/auth/status` tells the page whether to show the button; `GET /api/me` returns the signed-in member's tier and status.

`GET /api/ttt/mine` (member session only) powers the **My TTT** card on the profile page: the rider's own sign-up for the current week, and once line-ups are published their team(s), zone, captain, teammates, waitlist place and result, plus up to 10 earlier weeks they rode (from the archive). Line-ups stay hidden until published, exactly as on the TTT page.
